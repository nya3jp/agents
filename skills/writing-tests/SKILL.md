# テストの書き方

- **公開 API をテストする。**
  - テストから届くようにするためだけに内部を露出させない（ヘルパーのアクセサや `getFooForTesting()` など）。
  - 良いテストは、内部のリファクタリングを経ても変更なしで通り続ける。
- **テストダブルは次の順で選ぶ。**
  1. 実物の実装（例: 本物のコレクションや値オブジェクト、Robolectric の本物の Context、inflate した本物の View）
  2. 実際の振る舞いをモデル化した、再利用可能な fake
  3. mock は最後の手段に限る。mock は、テスト対象のコードがどのメソッドを呼ぶかを固定してしまうため。
- 依存先（例: JNI ブリッジや外部サービス）の fake を作るのが難しければ、個々のテストで mock するのではなく、それ自体のテストを持つ共有の fake を追加する。
- **テストヘルパーの内部の詳細に依存しない。** テストがヘルパーのある挙動を必要とするなら、それをヘルパーの文書化された契約にする。
- **すべてのバグ修正に回帰テストを付ける。** 修正なしでは失敗するテストにする。
- **失敗する経路もカバーする。** 重複登録、未知の入力、パースエラー、外部コマンドの失敗、キャンセルなど。
- **テストケースを互いに独立させる。** インストールした fixture や開いた Activity などの状態は、ケースの間で片付ける。
- **テストの重さを目的に合わせる。** unit テストで振る舞いを固定できるところに e2e テストを書かない。
- バイナリの fixture は、可能ならコミットせずにテスト時に生成する。
- 一時的に壊れているテストは、プロジェクトの無効化アノテーションとチケットを付けて無効にする。削除はしない。
- テストが CI で実際に実行されることを確認する。一部のスイートは特定のビルダーでしか動かず、明示的なオプトインが必要な場合がある。
- 新しいテストを実行し、正確なコマンドとその出力を報告する。
