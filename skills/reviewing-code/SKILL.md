# コードレビュー

## 見るべき点（優先順）

1. **設計**
   - 各クラスは知るべきことだけを知っているか。
   - 依存の向きは保たれているか。循環やレイヤ違反（例: UI 以外のコードが UI ツールキットに依存する）はないか。
   - ハードコードされた特別扱いや暗黙の挙動がどこかに隠れていないか。
   - 「汎用」のヘルパーが、実は呼び出し元固有の前提に依存していないか。
2. **正しさ**
   - 不変条件は assert されているか。
   - エラーが握りつぶされたり、黙って早期 return されたりしていないか。
   - null になり得ない値に不要な null チェックをしていないか。
   - ライフタイムと破棄の順序はどうなっているか。observer は登録解除されているか。`destroy()` は冪等か。
   - すべてのコールバックが必ず呼ばれるか。
   - コールバックに束縛した生ポインタや weak pointer が誤用され得ないか。
   - 非決定性（map の順序、stdout と stderr の混在、TOCTOU）、最悪計算量（例: visited チェックのない DFS）を確認する。
3. **契約と命名**
   - 公開 API に doc コメントがあり、null を返す条件、コールバックのタイミング、呼び出し側の義務が書かれているか。
   - 名前は正確か。オブジェクトを生成する `get*`、否定形の真偽値、紛らわしい似た名前、冗長な接尾辞に注意する。
   - 公開範囲は最小か。
4. **テスト**
   - テストは公開 API を通しているか。fake や実物で済むところで mock に頼っていないか。
   - 修正に回帰テストはあるか。失敗する経路はカバーされているか。
5. **変更の衛生**
   - CL を分割すべきではないか。
   - コミットメッセージは「なぜ」を説明しているか。
   - デバッグログやコメントアウトしたコードの消し忘れ、無関係な再フォーマット、import 漏れはないか。

## コメントのスタイル

- blocking なコメントにはラベルを付けない。軽微なコメントにだけ、軽微であることを示すラベルを先頭に付ける。
  - `nit:`
  - `nit&optional:`
  - `Optional:`
  - `No action required in this change:`
  - `FYI`
  - `qq:`
- 重大な問題があるときは、そのイテレーションでは重大なコメントだけを送り、軽微なコメントは次のイテレーション以降に回す。そのことを作者に明示する。`[major]` のようなラベルで重さを区別するより、このほうがよい。
- 具体的なコードを提案する（suggestion ブロック、シグネチャ、名前の候補）。根拠となるスタイルガイドやドキュメントへのリンクを添える。
- 設計はシナリオで確かめる。例: "If A is requested while B is animating, which wins? Is the callback called?"
- 自分の理解を述べたうえで訂正を促す（"IIUC ..."、"Please correct me if I'm wrong."）。自分が間違っていたら素直に認める。
- 本質的でない点でブロックしない。TODO とチケットを付けたうえでの「後続の変更で」を受け入れる。
- 温かく接する。作者に感謝し、良い点を指摘する。
- コメントは、そのレビュースレッドの言語で書く（通常は英語）。
