# API と境界の設計

## 大原則

### 優先順位: 正しさ、可読性、性能の順

設計では、正しく動くことが前提である。次にコードの可読性を優先し、実行時の性能はその後に考える。性能の最適化は必要になるまで行わない。

- 可読性を犠牲にする最適化（キャッシュ、可変な状態の使い回し、処理の手動のインライン化など）は、計測で必要だと示されてから入れる。入れるときは、計測値をコミットメッセージに書く。
- 可読性を損なわずに済む工夫は、最適化とはみなさずに最初から行ってよい。例: 安い検査を高い処理より先に行う。不要な外部プロセスの呼び出しを避ける。

### 単一責任の原則

設計原則の中で最も重要なのは単一責任の原則である。問題が直交した副問題に分解できるなら、コードやクラスもそれに応じて分割する。

- 責務を 1 文で説明できないクラスは分割を検討する。「A と B をする」と書きたくなったら、A と B が直交していないかを問う。
- 例: 1 つのインターフェースが、UI 以外のコードから UI を操作する用途と、UI 部品どうしのコールバックの用途の 2 つに使われていた。用途ごとにインターフェースを分けると、UI 以外のコードが UI の詳細に依存しなくなる。
- 可変なインスタンス変数が多いことは、複数の責務が 1 つのクラスに同居しているシグナルである。

以降の節は、これらの原則を具体的な場面に当てはめたものである。

## 境界と依存

依存は一方向にし、各層には知るべきことだけを知らせる。

- コードを書く前に、意図する依存の連鎖を描き、各層の責務を言語化する。
- 呼び出し側が実装の詳細を知る必要がないようにする。呼び出される側が自分で導出できるパラメータは削る。例: 機能フラグの値を引数で受け取るのではなく、フラグを参照する側で読む。
- 内部のフォーマットは、外部ツールに直接パースさせず、安定したバージョン付きの境界の裏に隠す。
- 設定値は、環境がどうであるか（`isLargeScreen`）ではなく、何をすべきか（`useKeyboardReadyUi`）を表す。環境から振る舞いを決める判断ロジックは、設定を作る 1 か所にまとめる。
- 汎用に見えるヘルパーは、本当に汎用でなければならない。特定の呼び出し元の前提に依存しているなら、用途に特化した名前と置き場所を与える。

## 契約

契約は、できるだけ型で表現する。型で表現するのが難しければ、公開 API のコメントに書く。

- 状態機械には sum type を使う。とり得ない組み合わせを型で表現できないようにする。
- 逆に他のライブラリを使うときは、理想的には、公開された契約にないことを仮定しない。ただし、どこまで守るかは場合による。

## 状態と不変性

状態は最小にし、できる限り不変にする。状態が少ないほど、ロジックの正しさを論じやすくなる。

- 言語が不変な変数の定義（`const`、`final`、`val`、`mut` なしの `let` など）を提供するなら、できる限り使う。ローカル変数はもちろん、特にクラスのインスタンス変数を不変にする。
- 可変なインスタンス変数を足す前に、他の値から導出できないか、引数やローカル変数で済まないかを検討する。
- 初期化の途中にだけ存在する状態は、ファクトリ関数を切り出して排除する。状態が変化しなくなった時点でインスタンスを作れば、クラスは初期化途中の状態を持たずに済む。これはよくあるケースである。
  - 例: ソケットの接続が完了してからソケットの所有権をインスタンスに渡せば、「接続中」という状態を排除できる。ただし、接続中にそのオブジェクトへアクセスする必要がないことが前提となる。
- リスナーが 1 つしかないなら、add/remove の登録の仕組みのために可変なリストを持たない。コンストラクタで受け取って不変なフィールドに保持する。
- インスタンスに状態を持たせざるを得ないときは、状態の間に成り立つ不変条件を assert などで宣言する。
- クラスは自分の状態と不変条件を自分で守る。外部のクラスが `AddX` や `RemoveX` を正しく呼ぶことに依存しない。

## 合成

振る舞いを変えるには、継承ではなく delegate や合成を使う。

- 複雑なフレームワークのクラスはサブクラス化しない。override が多い基底クラスは、正しさを論じにくくなる。避けられない場合は、最も単純な基底クラスを継承する。
- ヘルパーは合成しやすくする。出力（ファイル、環境変数、provider）を返し、アクションの実行は呼び出し側に任せる。呼び出しをラップして隠さない。

## 命名と引数

名前と引数は、呼び出し元だけを読んで正しく使えるように付ける。

- メソッドの名前は、getter、setter、何をするかを表す動詞（`UpdateFoo`、`GrantAccess`）にするのが基本である。`OnFoo` のようなイベント名は、observer のインターフェースで使うことが多い。
- デフォルト引数は慎重に使う。ほとんどの呼び出し元が同じ値を渡し、別の値を渡すべき場面が明らかな場合に限る。デフォルト値が不適切な呼び出しは、呼び出し元だけを見ても気づけないバグになるため。引数を増やすときに、パッチの変更行数を減らすためだけにデフォルト引数を使ってはならない。
