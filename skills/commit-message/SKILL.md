# コミットメッセージと変更の分割

## 分割

- 1 コミットにつき目的は 1 つにする。典型的な大きさは変更行数で約 50 行。約 350 行を超えたら分割を検討する。テストは本体より大きくなりがちなので、テストの行数は数えなくてよい。
- 次のものは別々のコミットにする。
  - 純粋なリファクタリングと、振る舞いの変更
  - 機械的なリネームと、手作業での後続の修正
  - Revert と、その修正
  - 順序やライフタイムに関わるリスクの高い変更と、それ以外
- リスクの高い振る舞いはフィーチャーフラグの裏に置き、既知の問題は後続のコミットで直し、デフォルトの切り替えはそれ単独のコミットで行う。
- シリーズでは、各コミットに全体の目的を書く（"This is a part of the patch series to <goal>."）。そのうえで、このステップが何をするかを書く。

## メッセージの構成

```
component: Imperative summary under 72 chars

<背景: 現状と、何が問題なのか>

<この変更が何をするか>

<検討した代替案と、採用しなかった理由（あれば）>

<既知の制約と今後の予定（"In a later patch, ..."）>

<リポジトリの慣習に従ったトレーラー（例: バグ番号、テスト方法）>
```

- メッセージ自体はリポジトリの慣習に従った言語で書く（通常は英語）。
- 本文は 72 桁で折り返す。
- 行ごとの「何をしたか」ではなく「なぜ」を説明する。関連する変更、チケット、上流の issue はリンクで参照する。
- 純粋なリファクタリングではそう明記する: "This is a pure refactoring. No functional changes are expected."
- 機械的なリネームでは、正確なスクリプト（sed と `git mv`）を載せ、レビュアーが再現できるようにする。
- UI の変更では、スクリーンショットのリンク用のプレースホルダを残す。
- 性能に関わる変更では、変更前後の計測値を載せる。
- 妥協した点は正直に書く。例: "I'm not fully comfortable with X, but ... to avoid yak shaving."
- TEST 行には実際に実行したコマンドを正確に書く。実行していないテストを実行したと書いてはならない。
- Revert には理由とチケットのリンクを書く。Reland には、何が問題だったかと、何を変えたかを書く。

リポジトリの既存のトレーラーと件名プレフィックスの慣習に従う。まず `git log` を確認すること。
